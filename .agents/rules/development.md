# BOOKMATE Development Rules

## 1. 기본 작업 원칙

- 현재 정상적으로 동작하는 코드를 불필요하게 수정하지 않는다.
- 요청받은 기능을 구현하기 위해 필요한 최소 범위만 수정한다.
- 리팩터링은 사용자가 명시적으로 요청하지 않는 한 진행하지 않는다.
- 기존 기능이 정상 동작하고 있다면 새로운 구현 방식으로 임의 교체하지 않는다.
- 기존 프로젝트 구조와 코딩 스타일을 우선 존중한다.

## 2. 코드 수정 전 분석

코드를 수정하기 전에 반드시 관련 코드를 먼저 확인한다.

다음 순서로 작업한다.

1. 현재 구현 구조를 확인한다.
2. 수정이 필요한 파일을 확인한다.
3. 기존 기능에 미치는 영향을 확인한다.
4. 최소 수정 방법을 선택한다.
5. 그 후 코드를 수정한다.

여러 파일에 영향을 주는 변경이라면,
코드를 수정하기 전에 다음 내용을 한국어로 간단히 설명한다.

- 현재 구조
- 수정할 파일
- 수정 이유
- 예상 영향 범위

## 3. 기존 코드 보존

- 기존 변수명, 함수명, 클래스명, API 경로를 임의로 변경하지 않는다.
- 기존 코드를 재사용할 경우 변수명을 임의로 변경하지 않는다.
- 이름 변경이 반드시 필요한 경우 이유를 먼저 설명한다.
- 사용자가 요청하지 않은 파일 이동 또는 파일명 변경을 하지 않는다.
- 사용자가 요청하지 않은 코드 정리, 포맷 변경, 대규모 리팩터링을 하지 않는다.
- 기존 정상 기능을 삭제하지 않는다.

## 4. 기능 추가 제한

- 사용자가 요청하지 않은 기능을 임의로 추가하지 않는다.
- "더 좋아 보인다"는 이유만으로 새로운 기능, 라이브러리, 프레임워크를 추가하지 않는다.
- 로그인, 회원가입, 인증, 관리자 기능 등을 임의로 추가하지 않는다.
- product.md에 없는 기능은 사용자의 요청 없이 구현하지 않는다.
- MVP 범위를 우선한다.

새로운 기능이 필요하다고 판단되는 경우 직접 구현하지 말고,
필요한 이유와 장단점을 먼저 설명한다.

## 5. BOOKMATE 문서 우선순위

BOOKMATE 프로젝트의 기준 문서는 다음과 같다.

1. product.md
2. ui.md
3. engineering.md

구현은 위 문서의 내용을 기준으로 한다.

문서와 코드가 충돌하는 경우 임의로 판단하여 큰 변경을 하지 않는다.

사용자가 명시적으로 요청하지 않는 한
product.md의 핵심 정책을 변경하지 않는다.

특히 다음 BOOKMATE 원칙을 유지한다.

- 책 1권 = 공개 북클럽 1개
- 같은 책의 질문을 사용자들이 공유한다.
- 사용자의 답변은 기본적으로 비공개이다.
- 사용자가 공개를 선택한 답변만 공개 저장한다.
- AI는 사용자를 대신해 생각하지 않고 생각을 확장시키는 역할을 한다.
- 독후감은 현재 사용자가 직접 작성한 생각을 기반으로 생성한다.
- 다른 사용자의 의견을 현재 사용자의 의견처럼 독후감에 포함하지 않는다.

## 6. 초보자 수준 설명

사용자는 개발 초보자라고 가정한다.

작업 결과를 설명할 때 다음을 지킨다.

- 한국어로 설명한다.
- 어려운 용어는 쉬운 말로 함께 설명한다.
- "무엇을 변경했는지"뿐 아니라 "왜 변경했는지"도 설명한다.
- 중요한 코드가 어떤 역할을 하는지 설명한다.
- 오류가 발생하면 오류 메시지만 보여주지 말고 원인과 해결 방법을 설명한다.
- 가능한 경우 데이터가 어떻게 이동하는지 흐름으로 설명한다.

예:

Frontend
→ FastAPI
→ Supabase

또는

사용자 답변
→ FastAPI
→ Gemini API
→ 후속 질문
→ Frontend

## 7. 여러 방법이 있는 경우

구현 방법이 여러 개라면 가장 단순하고 효율적인 방법을 먼저 제안한다.

필요한 경우 대안을 함께 설명하되 다음 순서로 설명한다.

1. 추천 방법
2. 추천 이유
3. 다른 방법
4. 각각의 장단점

MVP에서는 복잡성보다 유지보수성과 이해하기 쉬운 구조를 우선한다.

## 8. 의존성 및 기술 스택

새로운 라이브러리는 꼭 필요한 경우에만 추가한다.

라이브러리를 추가하기 전에 다음을 확인한다.

- 기존 기능으로 해결할 수 없는가?
- 표준 라이브러리로 해결할 수 없는가?
- 프로젝트 복잡도를 불필요하게 증가시키지 않는가?

사용자가 승인한 MVP 기술 스택을 우선 유지한다.

Frontend:
- HTML
- CSS
- Vanilla JavaScript

Backend:
- Python
- FastAPI
- uv

Database:
- Supabase PostgreSQL

AI:
- Gemini API

사용자의 요청 없이 React, Next.js 또는 다른 프레임워크로 변경하지 않는다.

## 9. 보안

- API Key, 비밀번호, Secret Key를 코드에 직접 작성하지 않는다.
- 실제 비밀정보는 .env에서 관리한다.
- .env 파일을 Git에 포함하지 않는다.
- .env.example에는 실제 비밀정보가 아닌 예시값만 작성한다.
- Gemini API Key를 Frontend에 노출하지 않는다.
- Supabase 관리자 권한이 있는 Secret Key를 Frontend에 노출하지 않는다.

## 10. 데이터베이스

DB 구조를 임의로 변경하지 않는다.

테이블 또는 컬럼 추가/삭제가 필요한 경우 먼저 다음을 설명한다.

- 변경이 필요한 이유
- 변경되는 테이블
- 기존 데이터에 미치는 영향

MVP의 기본 테이블은 다음과 같다.

- books
- questions
- public_answers

불필요한 테이블을 임의로 추가하지 않는다.

## 11. 테스트

기능 수정 후 가능한 범위에서 기존 기능이 깨지지 않았는지 확인한다.

외부 API 테스트에서는 실제 API 호출을 불필요하게 반복하지 않는다.

자동 테스트에서는 가능한 경우 다음을 Mock 처리한다.

- Gemini API
- Supabase 외부 호출

테스트 때문에 실제 Gemini API 사용량을 불필요하게 소비하지 않는다.

## 12. Git 작업

- 사용자의 명시적인 요청 없이 git commit 하지 않는다.
- 사용자의 명시적인 요청 없이 git push 하지 않는다.
- 기존 Git 히스토리를 변경하는 명령을 임의로 실행하지 않는다.
- reset --hard, force push 등 위험한 명령은 임의로 실행하지 않는다.

## 13. 작업 완료 보고

코드를 수정한 후에는 한국어로 간단히 다음 내용을 알려준다.

1. 변경한 파일
2. 변경한 내용
3. 변경한 이유
4. 테스트 또는 확인 결과
5. 주의할 점이 있다면 해당 내용

불필요하게 긴 설명보다 초보자가 변경 내용을 이해할 수 있는 설명을 우선한다.

## Token Efficiency

- 매 요청마다 프로젝트 전체를 다시 분석하지 않는다.
- 작업과 직접 관련된 파일만 우선 확인한다.
- product.md, ui.md, engineering.md 전체 재검토는 사용자가 요청한 경우에만 한다.
- 기존 대화에서 이미 확정된 내용을 불필요하게 반복 설명하지 않는다.
- 작은 수정에서는 전체 파일을 재작성하지 않고 필요한 부분만 수정한다.
- 작업 완료 보고는 기본적으로 간결하게 작성한다.
- 단순 작업에서는 장문의 계획, 분석 보고서, 코드 설명을 생성하지 않는다.
